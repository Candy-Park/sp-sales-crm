# 검토·결정 기록

이 문서는 조사 근거, 비교안, 잠정 의견, 미결정 사항을 관리한다. 확정된 주요 결정만 [기획서](../development-plan.md)에 반영하고, 실제 변경·검증 과정은 [작업 기록](../operations/2026-10-07-document-cleanup.md)에 남긴다.

## 2026-10-21 일반 메모 3건 보존·연결 범위 확정

사용자는 A(sp-sales-crm) 중심으로 일반 메모 3건을 보존·연결하는 최소 구현 계획을 요청했다. 전화 메모는 기존 문의에 합치지 않는 별도 할 일로 두고, 검수 기록과 용도 불명확한 로컬 3건은 그대로 보존한다고 확정했다. 실데이터 쓰기·앱 수정·배포 요청으로 확대하지 않는다.

[최소 구현 계획](memo-minimal-plan.md)은 기존 A 메모 저장/완료를 재사용하고 출처 JSON과 홈 표시 여부만 추가하는 작성자 제안이다. 개인/업무 메모 2건은 기존 메모에, 전화 항목만 홈 독립 할 일에 표시한다. B 원본은 유지하고 상시 양방향 연결·문의 병합은 구현하지 않는 안이다. 원본 ID·계정·개인 본문은 D 비공개 선택 목록/실행 준비 자료에서 다룬다. 실행 직전 소스 최신값·계정 재확인과 실제 적용 승인이 남아 있다.

기획서에는 확정 요구사항과 합격 기준만 반영했다. 구체적 스키마·UI·재시도·검수·복원은 계획, 문서 검증/보관은 기존 2026-10-21 작업 기록의 계획 작성 절에 남긴다. 이전 전체 통합 제안은 이력으로 보존한다.

## 2026-10-21 통합 기반 확정·읽기 전용 사전 점검

후속 상태: 사용자가 Chrome 로그인을 완료한 뒤 실제 원격 대조를 요청했고, 두 프로젝트의 문의·업무·메모를 읽기 조회했다. 현재 비교 범위의 확정 중복은 발견되지 않았으며, 일반 메모의 관련 문의 확인과 로컬 맥락 부족 기록은 보류했다. 원격 적용 상태가 최신 로컬 구현과 다른 점도 확인했다. 상세 데이터는 D의 비공개 `cloud-comparison-results.md` 및 증거 JSON에, 조회/문서 검증 과정은 아래 작업 기록의 후속 절에 남긴다.

작성자 권고는 A 중심 홈을 유지하고 B의 필요한 일반 메모부터 선별 보존·연결을 검토하는 것이다. 상시 양쪽 DB 조회/전체 이전을 곧바로 구현하는 것은 사용자 결정이 아니다. 계정 매핑·메모 연결·보류 기록의 용도와 실제 구현 범위는 다음 선택 사항으로 유지한다.

사용자는 sp-sales-crm을 통합 기반으로 선택했다. 다음 허용 범위는 Source Photonics CRM의 실제 사용 환경과 데이터 중복의 읽기 전용 확인이며, 결과를 본 뒤 앱 수정 여부를 결정한다. 기존 통합 계획의 B 연결 방식·연결대장·데이터 이전·배포까지 승인한 것으로 확대하지 않는다.

로컬·배포 환경표식은 직접 확인했고, 현재 원격 데이터 대조는 Supabase 인증 대기다. 사용자는 연결 후 원격도 확인하는 경로를 선택했으나 연결 성공은 아직 확인하지 못했다. 상세 과정·보류·재개 지점은 [읽기 전용 사전 점검 기록](../operations/2026-10-21-crm-readonly-audit.md)을 따른다. 실제 업무별 근거는 Git 밖의 D 산출물로 보관한다.

## 2026-10-20 두 CRM 기능·데이터 통합 검토

사용자는 sp-sales-crm과 Source Photonics CRM의 중복을 줄이고 메일·문의·오늘 할 일을 한곳에서 조회하는 1차 목표에 맞춰 대조표와 통합 계획을 완성하도록 요청했다. 앱 변경은 문서 확인 후 결정한다는 조건이다. 상세 근거·기능/데이터 대조·중복 판단·검수 기준은 [통합 계획](crm-integration-plan.md)에 모았다.

확정은 문서 작성 범위와 1차 목표다. A(sp-sales-crm) 기반+B 읽기 연결, 원본 DB 보존 후 선택적 이전은 작성자 권고이며 구현 승인이 아니다. 기존 기획의 sp-crm 별도 보존·통합 제외와 이번 후속 검토 범위를 구분한다. B의 초기 지침/기준 문서와 최신 구현·운영 기록의 상태 차이도 명시했다. 실데이터 중복 건수와 B 운영 환경·원격 스키마 적용 여부는 미확인이다.

계정/환경 매핑·PC 꺼짐 범위·연결대장 저장과 접근 방식은 다음 실행 전 결정한다. 앱·DB·인증·배포·Notion·원격 Git 변경 없이 문서만 작성한다. 작성·문서 검증·보관 결과는 [작업 기록](../operations/2026-10-20-crm-integration-planning.md)에 남긴다.

## 기록 방식

항목별로 검토일, 질문, 근거, 대안·잠정 의견, 결정 상태, 최종 결정을 구분한다. 잠정 의견과 조사 당시 조건을 확정 요구사항이나 현재 상태로 취급하지 않는다. 결제·요금 조사도 이 문서에서 관리하며, 실제 결제·계정 변경이 발생하면 작업 기록을 연결한다.

## 2026-10-07 문서 구분 결정

사용자 요청에 따라 기획서는 요구사항과 주요 결정만 유지한다. 결제 조사·잠정 의견은 검토·결정 기록, 백업·변경·검증 이력은 작업 기록으로 분리한다. 개발 보고서는 실제 구현이 시작된 이후 구현 결과를 보고할 때 작성한다. 조사·문서 정리만으로 개발 보고서를 작성하지 않는다.

## 설계 제안 — 이관 당시 내용

다음은 정리 전 기획서의 설계 제안이다. 구현 현황을 보고하는 자료가 아니며, 실제 구현 구조·검증은 개별 작업 기록을 따른다.

- 문의·메시지·Action을 별도 데이터로 관리하고 수집 메일은 사용자가 검토한 뒤 Inquiry에 연결한다.
- 구조화된 사양 필터부터 제공하고 의미 검색은 확장 시 검토한다.
- 공개 회원가입 기본 비활성, 정기 백업과 데이터 가져오기·스키마 변경 전 백업을 제안했다. 상세 운영 조건은 실제 계정·서비스 플랜과 회사 정책을 확인해 결정한다.
- 초안 전체 버전 관리 범위는 저장량과 사용성을 보고 결정한다.

### 논리 데이터 구조 제안

아래는 구현 전 확정할 논리 구조다. 모든 업무 데이터에는 식별자, owner_id, 생성·수정 시각을 두고 소유자 접근을 검사한다. 시각은 UTC 저장, 사용자 표시는 Asia/Seoul을 기본으로 한다.

| 데이터 | 핵심 항목·관계 |
|---|---|
| Customer / Contact | 고객사, 담당자, 업무 연락처; 담당자는 고객사와 연결 |
| Project | 고객사, 프로젝트명, 설명·진행 메모 |
| Inquiry | 제목, 접수 채널·시각, 고객·담당자·프로젝트, 대표 상태, 요구사양, Next Action |
| Message | Inquiry 연결, 방향·채널, 발신/수신자, 원문, 제목, 실제 발송/수신 시각, 수집 식별자 |
| Requirement | 사양명·값·단위, 원문 근거, AI 제안/사용자 확인 여부, 미확인 내용 |
| Product / Source | P/N, 제품명, 주요 사양, Active/EOL/Development 또는 Unknown, PLM Owner, 출처·자료일·Last Confirmed |
| Inquiry Product | 문의와 후보 연결, 선택/확인 필요, 선택 근거·확인일 |
| HQ Question / Response | 질문과 관련 답변 메시지 연결, 답변됨/부분 답변/미답변, 사용자 검토 |
| Draft | HQ/고객 초안·번역·요약, 근거 메시지, 사용자 수정본, 생성 시각·모델 정보 |
| Action | Inquiry, 종류, 내용, 기한, 완료/취소, 대기 대상·시작일 |
| Sync Receipt | Agent·메일 식별자, 수집/반영 결과, 오류·마지막 성공 시각 |

하나의 Inquiry에 여러 메시지·후보·HQ 질문·Action을 연결한다. 원문을 번역·요약으로 덮어쓰지 않는다. 고객·프로젝트 변경으로 기존 문의를 삭제하지 않는다. 가격·납기는 후보 제품의 일반 확정값으로 저장하지 않고 해당 문의에서 확인 출처·확인일과 함께 기록한다.

원문·최종 답변·발송 기록은 MVP부터 보존한다. 상세 변경 이력 UI가 다음 버전이라는 이유로 원천 데이터를 버리지 않는다. 초안 전체 버전 관리의 범위는 구현 시 저장량과 사용성을 고려해 확정한다.

### 시스템 역할 제안

웹 CRM은 문의·제품 검색·Action·초안 기능을 제공한다. Workers API는 접근통제·업무 규칙·AI 호출·수집 요청을 처리하고 Supabase는 로그인과 업무 데이터를 관리한다. 로컬 Agent는 지정 Outlook 범위에서 읽은 메일을 전송한다. 서비스 권한 키와 AI 키를 브라우저에 제공하지 않는다.

자동 판단으로 실제 메일을 제외하거나 삭제하지 않는다. 제외는 목록 필터이며 원문·영수증·보류 상태를 보존하고 재수집으로 해제하지 않는다. 이미 연결된 메일은 제외할 수 없다. 늦은 재시도가 사용자의 이후 복원을 덮지 않도록 검토 버전을 확인한다. 이 단계에서는 AI 호출·자동 발송·백그라운드 자동 실행·인증정보 저장을 추가하지 않는다.

## 2026-10-07 오늘 수신 메일로 분류 기준 확대 확정

사용자는 오늘 도착한 메일 전체를 검토하고 확장하라고 요청한 뒤, 기능·과거 기간 확대보다 고객사 업무/HQ 업무/스팸 등의 분류 학습이 목적이라고 명확히 했다. 명시적으로 실행한 오늘 받은 편지함 검토로 분류 제안과 사용자 확인·수정을 축적한다. 별도 정크 폴더나 전체 사서함 자동 처리로 범위를 확대하지 않는다.

상대의 업무 관계와 메일 목적을 분리한다. 서비스 알림에 들어 있는 고객/HQ 표현이나 인용문을 최신 발신자의 업무 관계로 오인하지 않는다. 외부 파일 공유는 업무 관계 확인 전 스팸 확정으로 쓰지 않는다. 사용자가 이번 검토의 공유 메일 2건을 관계없는 스팸으로 확인했으며, 해당 고유 메일만 정답 사례로 기록한다. 서비스 도메인 전체에 적용하는 차단 규칙으로 일반화하지 않는다. 개별 제목·발신자·본문·정답 키는 공유 Git에 보관하지 않는다.

현재는 로컬 규칙·본문 신호 기반 제안과 확정 사례 보존이다. 실제 AI 모델 훈련·서비스 호출을 구현한 것으로 보고하지 않는다. 문의 연결·업무 제외·삭제·자동 발송은 이 분류 확인과 별도이며 기존 수동 검토 요구사항을 유지한다. 실제 결과·검사·보존 범위는 Outlook 작업 기록에 남긴다.

### 2026-10-07 후속 분류 기준 검토 — 제안과 정답 구분

사용자가 결과 확인 후 다음 스텝을 요청했다. CRM 화면 연결을 검토하는 과정에서 확정 사례가 스팸 2건에만 편중된 점을 확인했다. 분류 학습 목적에 맞춰 기존 승인 기간의 보존된 받은 메일도 로컬에서 비교하고, 고객/HQ/자동 알림의 구분을 검증하는 단계를 먼저 진행한다. 새로운 폴더 수집·전체 사서함 AI 전송·업무 상태 자동 처리로 확대하지 않는다.

조사 결과 같은 회사 도메인에도 출하·주문·ECN·승인 지연·주간 보고 자동 알림이 섞여 있다. 본문에 인용된 고객이나 제목의 고객 태그는 발신 상대와 별개다. 도메인/태그만으로 고객 업무를 확정하거나 내부 발신을 모두 담당자의 직접 답변으로 간주하면 오분류가 생긴다. 내부 Exchange 표기는 원본을 변경하지 않고 별도 읽기 전용 도메인 조회로 보완한다. 정확한 회사 도메인·태그가 있어도 업무 분류는 후보로 두며 중요 알림을 자동 스팸 제외하지 않는다.

수집된 문서의 본문 신호는 전체 의미 판단·답변 충분성·발신 인증을 대체하지 않는다. 현재 두 스팸 정답만으로 고객/HQ 분류 정확도를 주장하지 않는다. 대표 HQ 업무와 전시회 재예약 사례의 업무 관계 확인을 요청했으며, 답변 전에는 제안 상태를 유지한다. 실제 사례의 제목/상대/고유 키·개인 설정은 ignored notes와 D 자료에만 보관한다. 분류별 정답·독립 평가 사례와 AI 서비스/모델/비용 결정을 확보한 뒤 실제 AI 적용을 검토한다. CRM 분류 화면과 오늘 신규 로컬 원문의 서버 연결은 아직 구현·반영 결과로 주장하지 않는다.

## 2026-10-07 분류 검토 화면 연결 결정

사용자가 후속 분류 결과를 확인한 뒤 다음 스텝과 계속 진행을 요청했다. 이미 승인한 분류 학습 목적에 따라 로컬 제안을 CRM에서 보고 직접 확정·수정하는 하위 작업을 진행한다. 오늘 검토본의 신규 4건은 같은 새 Supabase에 로그인한 CRM의 명시적 연결 버튼으로 전송한다. 원문 전체의 새 AI 전송, 신규 폴더 수집이나 자동 실행으로 확대하지 않는다.

제안과 사용자 확정은 별도 이력으로 저장한다. 상대 관계와 업무 목적을 분리하고, 명시적으로 확인한 스팸 2건의 관계는 미확인으로 둔다. 기존 사용자 수정이 있으면 최초 확인 사례를 재연결하며 덮지 않는다. 대표 HQ 업무·전시회 관계 질문은 답변 전 제안 상태를 유지한다. 분류 확인을 문의 연결·업무 제외와 결합하지 않는다.

새 조회 view는 원본 테이블과 분류 이력의 소유자 RLS를 따르는 security_invoker 방식으로 구성한다. 근거: [Supabase RLS 공식 문서](https://supabase.com/docs/guides/database/postgres/row-level-security), [함수 권한 공식 문서](https://supabase.com/docs/guides/database/functions). Supabase 커넥터는 연결되어 있지 않아 기존에 로그인한 Chrome의 해당 새 프로젝트 SQL Editor로 증분 변경과 검증을 수행한다. 기존 제품/회신/수집 DDL은 반복하지 않는다. 실제 적용·전송·검증 상태는 작업 기록을 따른다.

## 2026-10-07 별도 로컬 업무 DB 복원 방식

Git 제외 개인 .env·메일/DB 원본·캐시/백업·인증정보는 제출 파일이 아니며 공개하지 않는다. 기존 로컬 전용 Git 결정은 이 소스 제출 범위에 한해 변경한다. 외부 웹 운영 배포·Cloudflare 계정 변경·PC 원격 접근 설정/새 권한 생성은 승인에 포함하지 않는다. 가상 데이터 시연2장은 제출 설명과 함께 포함한다.

### 2026-10-13 — 외부 CRM 접속·보유 도메인·무료 방식 검토(미확정)

사용자는 외부주소로CRM 접속을요청하고 ajsol.co.kr/ajsol.net 도메인만보유했다고정정했다. 기존홈페이지보유를전제하지않는다. 홈페이지/CRM을만들어 도메인에연결할수있으며등록대행사와호스팅업체는별개다. 도메인선택은아직미확정이며유료전환허용은없다.

### 2026-10-13 — 무료 외부 접속 설계·직접 구현 승인(확정)

위 미확정 검토 이후 사용자는 PC가 꺼져도 저장된 업무를 조회·수정하는 방식을 선택하고 remote-access-design.md의 Cloudflare Free + 기존 Supabase + PC Outlook 분리를 승인했다. remote-access-plan.md 순서에 따라 이 대화에서 직접 구현·검수하는 실행도 승인했다. workers.dev 무료 기본 주소를 사용하며 ajsol.co.kr/ajsol.net의 DNS 변경과 유료 전환은 승인하지 않았다.

사용자가 Chrome에 로그인하고 공식 Wrangler의 계정 조회·Workers 배포 최소 OAuth 권한을 승인했다. 배포 인증은 Windows Credential Manager와 암호화된 Wrangler 파일에 보관한다. CRM PC Agent의 업무 계정 인증은 기존 로그인에서 전달한 검증된 액세스 토큰을 메모리에만 유지한다. CRM 자격증명을 OS에 영구 저장하거나 전역 예약/자동 시작을 추가하지 않는다. 기존 SQLite 메모가 없는 현재 계정에서 클라우드 메모를 기준으로 전환하고 로컬 자료는 보존한다.

구현·운영 적용·검증 결과는 기획서가 아닌 [외부 접속 작업 기록](../operations/2026-10-13-remote-access.md)에 남긴다.

### 2026-10-22 — 영수증 사진·경비 리스트 기능 보류(확정)

사용자는 기존 Source Photonics CRM(B)의 영수증 사진·리스트 기능을 sp-sales-crm으로 가져오는 계획을 요청했다가, 다른 업무(AJSOL)와 중복된다는 이유로 당분간 보류했다. 이번 결정으로 앱·DB·문서 기획 범위에 영수증 기능을 추가하지 않는다.

보류 전 확인한 사실: B의 영수증 기능은 사진 OCR(브라우저 내 한·영 인식) → 사용자 확인 → 원본 사진은 본인 Google Drive 비공유 폴더, DB에는 날짜·사용처·목적·금액·통화와 Drive 파일 ID만 저장 → 엑셀 내보내기 구조다. 10/21 원격 대조에서 B 클라우드 DB에는 영수증 테이블이 없어 실제 운영 적용은 확인되지 않았다. 사용자의 실제 경비 정산은 출장 단위가 아니라 월별 회사 경비 시스템 제출이며, 월별 사용내역 표와 종류별(식사·접대/주유/주차/기타) 영수증 분류를 사용한다. A의 `sales_remote_receipt`는 API 재시도 영수증으로 B의 경비 영수증과 다른 데이터다([통합 계획 C12](crm-integration-plan.md)).

잠정 의견(재개 시 참고): 그대로 이식하기보다 월별 사용내역 표 형식에 맞추고, 접대비의 고객사를 CRM 고객에서 선택하는 방식이 CRM 고유의 이점이다. 재개는 사용자가 다시 요청할 때 범위·중복 여부부터 정한다.

### 2026-10-22 — 출근 준비 AI비서 화면 검토(제안, 미확정)

사용자가 별도로 만든 로컬 '출근 준비 AI비서' 웹사이트가 직관적이라며 CRM 기획에 쓸 만한 점을 검토하도록 요청했다. 그 사이트는 오늘 일정 → 우선할 일 → 중요 메일 → 회의 준비 자료 → 확인 필요 순서의 브리핑, 실행 버튼 하나, 날짜별 보관함·실행 이력, 단순한 설정 화면으로 구성된다. 화면 조회만 했고 브리핑 실행·설정 저장은 하지 않았다.

CRM 홈에 참고할 후보 6가지(제안):

1. 정해진 읽기 순서: 오늘·기한 초과 할 일 → 새 요청·판단 필요 → 대기 → 확인 필요.
2. 우선할 일마다 이유 한 줄과 원문 근거 링크. 기한·고객·Action 종류로 규칙 기반 생성(AI 불필요).
3. 항목별 '확인/제안' 배지로 저장된 값과 메일 기반 제안을 구분.
4. '확인 필요' 칸으로 조회하지 못한 범위를 명시(조회 실패를 0건으로 표시하지 않는 기존 규칙의 화면 표현).
5. PC 연결·Outlook·마지막 동기화를 한 상자로 모은 연결 상태 칸.
6. 큰 제목·넓은 여백·번호 섹션과 주 버튼 하나의 단순한 화면.

주의: 하루 전체 브리핑·날짜별 보관함·캘린더 연동은 출근 비서와 중복되므로 CRM에 넣지 않는 것을 권고한다. CRM은 고객 문의를 끝까지 처리하는 곳으로 두고, 연결은 브리핑의 견적 메일 옆 'CRM에서 열기' 링크 정도로 검토한다. 이 검토는 구현 승인이 아니며 적용 범위는 사용자가 정한다.

### 2026-10-22 — 홈 브리핑 6가지 적용 승인(확정)

사용자가 위 출근 준비 AI비서 검토의 6가지를 CRM 홈에 적용하도록 요청했다. 적용 범위는 화면 순서·우선할 일과 이유·확인/제안 배지·확인 필요 칸·연결 상태 칸·주 버튼과 번호 섹션이다. 우선할 일의 이유는 저장된 Action의 기한·종류와 메일 관측만으로 규칙 기반으로 만들며 AI·DB·API 변경은 하지 않는다. 날짜별 보관함과 캘린더 연동은 포함하지 않는다. 운영 배포는 별도 확인 후 진행한다. 구현·검증은 [작업 기록](../operations/2026-10-22-home-brief.md)에 남긴다.

### 2026-10-23 — 외부 CRM "이 PC에서 로그인 유지" 추가(확정)

사용자는 테스트 중 새로고침마다 로그인하는 불편을 이유로 외부 CRM의 로그인을 없애 달라고 요청했다. 외부 주소는 누구나 열 수 있어 실제 고객·주문·메일 내용이 공개되고, 로그인 없이 데이터를 주려면 서버에 DB 관리자 키를 넣어야 하므로 권고하지 않았다. 사용자는 대안으로 "이 PC Chrome에서는 새로고침해도 로그인 유지"를 선택했다.

로그인 창에 "이 PC에서 로그인 유지" 체크박스를 두고, 체크한 브라우저에만 Supabase 세션을 저장한다. 다시 열 때도 서버의 계정 권한 확인(/api/me)을 통과해야 복원하며, 권한 거부·만료 시 저장 세션을 지운다. 로그아웃하면 저장된 로그인도 지운다. 체크하지 않으면 기존처럼 메모리에만 둔다. 기존 기획의 "인증정보 영구 보관 제외" 결정은 이 사용자 선택 범위에서 변경한다(비밀번호는 저장하지 않고 갱신 가능한 로그인 세션만 저장). 브라우저 저장 세션은 같은 PC를 쓰는 사람이 열 수 있으므로 공용 PC에서는 체크하지 않는다.

### 2026-10-23 — 홈이 눈에 안 들어오는 이유 점검과 목업 v3(제안, 미확정)

사용자가 배포된 홈이 한눈에 들어오지 않는데 색 문제인지 구조 문제인지 물었다. 실제 로그인 화면을 사용자 입장에서 본 의견은 구조 7 : 색 3이다.

- 구조: 할 일 문장이 두 줄짜리 원문이라 고객·할 일·기한이 묻힌다. 첫 화면 큰 카드가 숫자만 보여 주고 할 일은 스크롤해야 보인다. 같은 건수가 세 곳(요약 카드 좌·우, 카드 머리)에 반복된다. 카드마다 회색 안내문이 많다.
- 색: 연두→연보라 유리 배경 위에 베이지·흰 카드가 겹쳐 색 면이 경쟁하고 경계가 흐리다. 남색 강조가 많아 실제 강조점이 드러나지 않는다.

사용자 요청으로 목업 v3를 만들었다(정적 HTML, 앱·Git 밖 D 출력 폴더 보관). 할 일을 "고객 · 할 일 + 기한 배지" 한 줄로 줄이고 원문은 펼쳐 보기, 첫 화면에 할 일 3개, 건수는 상단 한 줄에만, 단색 밝은 배경과 '기한 지남'에만 빨간색, 안내문 제거. 실제 앱 적용 범위와 짧은 제목 생성 규칙은 사용자 확인 후 정한다.

### 2026-10-23 — 홈 v3 적용 승인(확정)

사용자가 목업 v3(회사 로고 반영)를 보고 "진행해"로 실제 앱 적용과 로그인 유지 기능의 함께 배포를 승인했다. 홈을 "오늘 할 일" 제목 + 주 버튼, 상태 한 줄, 할 일 3개(업무 제목 + 기한 배지, 설명은 첫 구절만·원문 펼침), 답변 대기·확인 필요 두 칸, 나머지 접기로 바꾸고 홈에서는 단색 배경을 쓴다. 할 일의 짧은 제목은 문장을 자동 요약하지 않고 이미 저장된 업무 제목을 쓴다. 다른 메뉴의 Frosted 테마는 유지한다. 1차 홈 브리핑의 확인/제안 배지는 홈 첫 화면에서는 기한 배지(새 메일·새 요청 포함)로 대체하고 접힌 전체 업무 목록에는 유지한다.

### 2026-10-23 — 외부 CRM 짧은 주소(확정)

사용자가 주소가 길다며 줄이기를 요청했다. 선택지는 ① Worker 이름 변경(`crm.piaoenya.workers.dev`, 무료) ② 계정 workers.dev 하위 이름까지 변경(계정의 모든 Worker 주소 변경) ③ 보유 도메인 연결(가장 짧지만 네임서버 이전과 메일 MX 이전 위험, 10/13 DNS 변경 미승인)이었다. 사용자는 ①을 선택했다. Worker 이름을 `crm`으로 바꿔 새 Worker로 배포하고, PC 수집 연결 주소와 주소 허용 검사를 새 주소로 바꾼다(전환 기간에는 기존 주소도 허용). 기존 `sp-sales-crm` Worker 삭제는 별도 확인 후 진행한다.

### 2026-10-23 — 기존 주소 유지 기간(확정)

사용자는 새 주소(`crm.piaoenya.workers.dev`)를 약 1주일 써 본 뒤 기존 Worker `sp-sales-crm`(sp-sales-crm.piaoenya.workers.dev)을 지우기로 했다. 그때까지 기존 주소는 삭제하지 않는다. 삭제할 때는 PC 수집 연결의 주소 허용 검사에서 기존 이름 허용도 함께 정리한다.
