# 검토·결정 기록

이 문서는 조사 근거, 비교안, 잠정 의견, 미결정 사항을 관리한다. 확정된 주요 결정만 [기획서](../development-plan.md)에 반영하고, 실제 변경·검증 과정은 [작업 기록](../operations/2026-10-07-document-cleanup.md)에 남긴다.

## 기록 방식

항목별로 검토일, 질문, 근거, 대안·잠정 의견, 결정 상태, 최종 결정을 구분한다. 잠정 의견과 조사 당시 조건을 확정 요구사항이나 현재 상태로 취급하지 않는다. 결제·요금 조사도 이 문서에서 관리하며, 실제 결제·계정 변경이 발생하면 작업 기록을 연결한다.

## 2026-10-07 문서 구분 결정

사용자 요청에 따라 기획서는 요구사항과 주요 결정만 유지한다. 결제 조사·잠정 의견은 검토·결정 기록, 백업·변경·검증 이력은 작업 기록으로 분리한다. 개발 보고서는 실제 구현이 시작된 이후 구현 결과를 보고할 때 작성한다. 조사·문서 정리만으로 개발 보고서를 작성하지 않는다.

## 설계 제안 — 이관 당시 내용

다음은 정리 전 기획서의 설계 제안이다. 구현 현황을 보고하는 자료가 아니며, 실제 구현 구조·검증은 개별 작업 기록을 따른다.

- 문의·메시지·Action을 별도 데이터로 관리하고 수집 메일은 사용자가 검토한 뒤 Inquiry에 연결한다.
- 구조화된 사양 필터부터 제공하고 의미 검색은 확장 시 검토한다.
- 공개 회원가입 기본 비활성, 정기 백업과 데이터 가져오기·스키마 변경 전 백업을 제안했다. 상세 운영 조건은 실제 계정·서비스 플랜과 회사 정책을 확인해 결정한다.
- 초안 전체 버전 관리 범위는 저장량과 사용성을 보고 결정한다.

### 논리 데이터 구조 제안

아래는 구현 전 확정할 논리 구조다. 모든 업무 데이터에는 식별자, owner_id, 생성·수정 시각을 두고 소유자 접근을 검사한다. 시각은 UTC 저장, 사용자 표시는 Asia/Seoul을 기본으로 한다.

| 데이터 | 핵심 항목·관계 |
|---|---|
| Customer / Contact | 고객사, 담당자, 업무 연락처; 담당자는 고객사와 연결 |
| Project | 고객사, 프로젝트명, 설명·진행 메모 |
| Inquiry | 제목, 접수 채널·시각, 고객·담당자·프로젝트, 대표 상태, 요구사양, Next Action |
| Message | Inquiry 연결, 방향·채널, 발신/수신자, 원문, 제목, 실제 발송/수신 시각, 수집 식별자 |
| Requirement | 사양명·값·단위, 원문 근거, AI 제안/사용자 확인 여부, 미확인 내용 |
| Product / Source | P/N, 제품명, 주요 사양, Active/EOL/Development 또는 Unknown, PLM Owner, 출처·자료일·Last Confirmed |
| Inquiry Product | 문의와 후보 연결, 선택/확인 필요, 선택 근거·확인일 |
| HQ Question / Response | 질문과 관련 답변 메시지 연결, 답변됨/부분 답변/미답변, 사용자 검토 |
| Draft | HQ/고객 초안·번역·요약, 근거 메시지, 사용자 수정본, 생성 시각·모델 정보 |
| Action | Inquiry, 종류, 내용, 기한, 완료/취소, 대기 대상·시작일 |
| Sync Receipt | Agent·메일 식별자, 수집/반영 결과, 오류·마지막 성공 시각 |

하나의 Inquiry에 여러 메시지·후보·HQ 질문·Action을 연결한다. 원문을 번역·요약으로 덮어쓰지 않는다. 고객·프로젝트 변경으로 기존 문의를 삭제하지 않는다. 가격·납기는 후보 제품의 일반 확정값으로 저장하지 않고 해당 문의에서 확인 출처·확인일과 함께 기록한다.

원문·최종 답변·발송 기록은 MVP부터 보존한다. 상세 변경 이력 UI가 다음 버전이라는 이유로 원천 데이터를 버리지 않는다. 초안 전체 버전 관리의 범위는 구현 시 저장량과 사용성을 고려해 확정한다.

### 시스템 역할 제안

웹 CRM은 문의·제품 검색·Action·초안 기능을 제공한다. Workers API는 접근통제·업무 규칙·AI 호출·수집 요청을 처리하고 Supabase는 로그인과 업무 데이터를 관리한다. 로컬 Agent는 지정 Outlook 범위에서 읽은 메일을 전송한다. 서비스 권한 키와 AI 키를 브라우저에 제공하지 않는다.

- 운영 배포 계정·호스팅 설정, Agent 운영 방식과 실제 수집 연결.
- 제품 판매 상태·최신본 여부 확인 기준과 후속 제품군 확대.

- 기술·실자료 검증 결과에 따른 목표 일정 재검토. 위 날짜는 확정 약속이 아니다.

## 2026-10-07 Outlook 실행·긴 본문 처리 확정

사용자가 “추천대로 진행해”라고 승인했고 후속 작업 요청에서 재확인했다. 로그인한 CRM에서 사용자가 직접 수집을 시작하는 방식으로 먼저 구현·검증한다. 인증정보 영구 보관과 PC 백그라운드 자동 실행은 포함하지 않는다.

본문 100,000자 초과 4건은 로컬 원문을 그대로 보존하고 CRM에 보류로 표시한다. 나머지 334건부터 서버 대기 목록에 연결한다. 수집된 메일은 사용자가 검토하여 신규 또는 기존 문의에 연결하며 제목만으로 자동 병합하거나 메일마다 문의를 만들지 않는다.

실제 구현·검증 결과는 [작업 기록](../operations/2026-10-07-outlook-collection.md)에 관리한다.

## 2026-10-07 수집 메일의 업무 제외·복원 확정

사용자가 정크/광고 메일과 AI 토큰 낭비를 우려했다. 현재 수집은 기본 받은/보낸 편지함의 승인 기간에 한정하며 정크 폴더를 읽지 않는다. 받은 편지함에 광고·알림이 섞일 수 있으므로 수동 업무 제외·복원, 실제 업무 메일의 문의 연결, AI 서비스·모델·비용 결정 순서를 제안했다. 사용자가 “그 다음 해야할일 해”라고 요청하여 첫 하위 작업인 업무 제외·복원을 진행한다.

자동 판단으로 실제 메일을 제외하거나 삭제하지 않는다. 제외는 목록 필터이며 원문·영수증·보류 상태를 보존하고 재수집으로 해제하지 않는다. 이미 연결된 메일은 제외할 수 없다. 늦은 재시도가 사용자의 이후 복원을 덮지 않도록 검토 버전을 확인한다. 이 단계에서는 AI 호출·자동 발송·백그라운드 자동 실행·인증정보 저장을 추가하지 않는다.

## 2026-10-07 오늘 수신 메일로 분류 기준 확대 확정

사용자는 오늘 도착한 메일 전체를 검토하고 확장하라고 요청한 뒤, 기능·과거 기간 확대보다 고객사 업무/HQ 업무/스팸 등의 분류 학습이 목적이라고 명확히 했다. 명시적으로 실행한 오늘 받은 편지함 검토로 분류 제안과 사용자 확인·수정을 축적한다. 별도 정크 폴더나 전체 사서함 자동 처리로 범위를 확대하지 않는다.

상대의 업무 관계와 메일 목적을 분리한다. 서비스 알림에 들어 있는 고객/HQ 표현이나 인용문을 최신 발신자의 업무 관계로 오인하지 않는다. 외부 파일 공유는 업무 관계 확인 전 스팸 확정으로 쓰지 않는다. 사용자가 이번 검토의 공유 메일 2건을 관계없는 스팸으로 확인했으며, 해당 고유 메일만 정답 사례로 기록한다. 서비스 도메인 전체에 적용하는 차단 규칙으로 일반화하지 않는다. 개별 제목·발신자·본문·정답 키는 공유 Git에 보관하지 않는다.

현재는 로컬 규칙·본문 신호 기반 제안과 확정 사례 보존이다. 실제 AI 모델 훈련·서비스 호출을 구현한 것으로 보고하지 않는다. 문의 연결·업무 제외·삭제·자동 발송은 이 분류 확인과 별도이며 기존 수동 검토 요구사항을 유지한다. 실제 결과·검사·보존 범위는 Outlook 작업 기록에 남긴다.

### 2026-10-07 후속 분류 기준 검토 — 제안과 정답 구분

사용자가 결과 확인 후 다음 스텝을 요청했다. CRM 화면 연결을 검토하는 과정에서 확정 사례가 스팸 2건에만 편중된 점을 확인했다. 분류 학습 목적에 맞춰 기존 승인 기간의 보존된 받은 메일도 로컬에서 비교하고, 고객/HQ/자동 알림의 구분을 검증하는 단계를 먼저 진행한다. 새로운 폴더 수집·전체 사서함 AI 전송·업무 상태 자동 처리로 확대하지 않는다.

조사 결과 같은 회사 도메인에도 출하·주문·ECN·승인 지연·주간 보고 자동 알림이 섞여 있다. 본문에 인용된 고객이나 제목의 고객 태그는 발신 상대와 별개다. 도메인/태그만으로 고객 업무를 확정하거나 내부 발신을 모두 담당자의 직접 답변으로 간주하면 오분류가 생긴다. 내부 Exchange 표기는 원본을 변경하지 않고 별도 읽기 전용 도메인 조회로 보완한다. 정확한 회사 도메인·태그가 있어도 업무 분류는 후보로 두며 중요 알림을 자동 스팸 제외하지 않는다.

수집된 문서의 본문 신호는 전체 의미 판단·답변 충분성·발신 인증을 대체하지 않는다. 현재 두 스팸 정답만으로 고객/HQ 분류 정확도를 주장하지 않는다. 대표 HQ 업무와 전시회 재예약 사례의 업무 관계 확인을 요청했으며, 답변 전에는 제안 상태를 유지한다. 실제 사례의 제목/상대/고유 키·개인 설정은 ignored notes와 D 자료에만 보관한다. 분류별 정답·독립 평가 사례와 AI 서비스/모델/비용 결정을 확보한 뒤 실제 AI 적용을 검토한다. CRM 분류 화면과 오늘 신규 로컬 원문의 서버 연결은 아직 구현·반영 결과로 주장하지 않는다.

## 2026-10-07 분류 검토 화면 연결 결정

사용자가 후속 분류 결과를 확인한 뒤 다음 스텝과 계속 진행을 요청했다. 이미 승인한 분류 학습 목적에 따라 로컬 제안을 CRM에서 보고 직접 확정·수정하는 하위 작업을 진행한다. 오늘 검토본의 신규 4건은 같은 새 Supabase에 로그인한 CRM의 명시적 연결 버튼으로 전송한다. 원문 전체의 새 AI 전송, 신규 폴더 수집이나 자동 실행으로 확대하지 않는다.

제안과 사용자 확정은 별도 이력으로 저장한다. 상대 관계와 업무 목적을 분리하고, 명시적으로 확인한 스팸 2건의 관계는 미확인으로 둔다. 기존 사용자 수정이 있으면 최초 확인 사례를 재연결하며 덮지 않는다. 대표 HQ 업무·전시회 관계 질문은 답변 전 제안 상태를 유지한다. 분류 확인을 문의 연결·업무 제외와 결합하지 않는다.

새 조회 view는 원본 테이블과 분류 이력의 소유자 RLS를 따르는 security_invoker 방식으로 구성한다. 근거: [Supabase RLS 공식 문서](https://supabase.com/docs/guides/database/postgres/row-level-security), [함수 권한 공식 문서](https://supabase.com/docs/guides/database/functions). Supabase 커넥터는 연결되어 있지 않아 기존에 로그인한 Chrome의 해당 새 프로젝트 SQL Editor로 증분 변경과 검증을 수행한다. 기존 제품/회신/수집 DDL은 반복하지 않는다. 실제 적용·전송·검증 상태는 작업 기록을 따른다.

## 2026-10-07 남은 단계의 연속 진행 승인

업무 단계는 최신 본문과 같은 scope/conversation 식별자의 수집 기록으로 제안한다. 제목이나 인용문으로 자동 병합하지 않으며 요청/중간 답변/후속 기록과 현재 처리 상태를 구분한다. 보낸 메일의 존재만으로 고객 전달·HQ 접수·승인·지급·출하를 확정하지 않는다. 조회 버튼은 분류 정답·문의·Action·발송 상태를 자동 변경하지 않는다.

## 2026-10-07 별도 로컬 업무 DB 복원 방식

## 2026-10-07 RMA 추적과 확장 순서 확정

사용자가 현재 RMA 건을 계속 추적하고 MVP 1차가 끝난 뒤 RMA 프로세스를 추가하도록 기획서에 반영하라고 지시했다. 확정 결정은 1차 범위를 유지하면서 RMA를 후속 확장으로 추가하고 실제 사례의 번호 발행부터 고객 검증까지 후속 업무를 추적하는 것이다. 구체적인 데이터 구조/화면·외부 연동 구현은 아직 착수하지 않는다.

실제 사례에서 전체 대상과 우선 반송/미회수 수량이 다르고, 번호 발행 이후 인보이스·예약·송장·공장 평가와 고객 재시험이 남는 것을 확인했다. 이에 사건/번호/개별 S/N/반송 배치와 단계별 근거를 구분하는 요구사항 및 검수 기준을 기획서에 반영했다. 개별 고객·메일·S/N·배송 정보는 ignored notes의 사례 기록에서 관리한다.

추적은 해당 사례의 새 회신·근거와 사용자 제공 물류/처리 정보를 읽기 전용으로 확인하고 중요한 변화·필요 조치만 알리는 범위다. 사용자의 DHL 직접 로그인·예약/제출, 원본 Excel 저장 및 최종 발송 판단은 유지한다. 별도 Outlook 서비스 설치·인증정보 영구 보관·자동 발송·AI API 호출·운영 DB 쓰기는 허용 범위로 확대하지 않는다.

## 2026-10-07 Auth/Storage 복원 검수 범위 재확인

기존 PGlite 복원은 public sales_*와 RLS용 사용자 UUID 호환 테이블 범위다. 실제 Auth 사용자/identity와 서비스 설정을 보존해 격리된 Auth 서비스에서 로그인·소유자 접근을 재검증해야 전체 Auth 복원으로 인정할 수 있다. 세션 건수나 UUID 호환 테이블만으로 인증 서비스 복원을 주장하지 않는다. 기존 운영 프로젝트에는 복원하지 않으며 인증정보를 로그/Git에 남기지 않는다.

[Supabase 백업 문서](https://supabase.com/docs/guides/platform/backups)에 따르면 DB 백업의 Storage 메타데이터와 객체 파일은 별도다. [로컬 복원 문서](https://supabase.com/docs/guides/local-development/restoring-downloaded-backup)는 Auth/Storage 등 서비스를 사용하는 로컬 스택 복원을 다룬다. 현재 신규 프로젝트의 Storage bucket/object는 0이지만 빈 상태 집계는 파일 복원 검수가 아니다. 향후 객체를 사용하는 시점에는 객체 바이트·메타데이터·접근정책과 실제 다운로드를 함께 검수해야 한다. Docker 엔진 가동 및 격리 서비스 복원 구성은 아직 실행하지 않았으며 새 원격·유료 플랜·운영 Auth 변경으로 확대하지 않았다.
