원문과 이전 검토 근거를 보존하고, 초안·복사를 실제 발송과 구분해 업무 상태 오판을 줄였다. 받은 답변만으로 질문을 완료하지 않으며 미답변/부분 답변이나 조회 실패·잘림이 있으면 문의 종료를 막는다. 저장 결과가 불확실할 때 입력과 요청 식별자를 유지한다.

수집 연결의 로컬 Node 72개·Python 35개 검사를 통과했고, 후속 업무 제외·복원까지 포함한 최종 검사는 Node 81개·Python 35개 및 브라우저 빌드다. API/회신 UI 테스트는 가상 네트워크 응답을 사용한다. 제품·회신 DB와 실제 로그인 화면에서 합성 자료의 업무 흐름을 검증했다. 실제 고객 회신·메일 발송 검수와 구분한다. 전체 MVP 완료를 의미하지 않는다.

메일 업무 제외·복원: 기본 업무/제외/전체 목록과 수동 제외·복원을 구현하고 새 DB에 증분 적용했다. 실제 DB의 합성 ROLLBACK 검사에서 영수증·제외 유지, 복원·늦은 재시도 충돌, 연결 제한, 원문 불변·소유자 접근통제를 확인했다. 실제 광고 검증 메일을 제외 → 제외 목록 조회/연결 폼 차단 → 승인 기간 재수집 후 제외 유지 → 복원까지 Chrome/DB에서 대조했다. 최종 제외 0, 해당 검토 버전 3. 연결된 업무 메일은 제외 버튼/신규 연결 폼이 숨겨진다. 기존 실제 338건의 식별/원문 집계 해시와 모든 로컬 영수증을 유지했다. 광고 일괄 자동 분류나 문의 자동 생성은 하지 않았다.

AI 서비스·모델·비용은 아직 선택하지 않아 호출하지 않는다. Outlook 다른 실메일의 기존 문의 연결·폴더 이동/답장/전달, 두 세션 경합·전체 DB 백업 복원 검증·1주 실사용은 남아 있다. 백그라운드 자동 실행·인증정보 영구 보관·배포는 이번 승인 범위에 포함하지 않는다. 기존 CRM과 Supabase sp-crm, 무료 플랜과 로컬 전용 Git 조건을 유지했다.

Outlook 로컬 큐의 백업·복원은 별도 D 사본에서 실제 검증했다. SQLite backup API → 새 경로 복원 → 재실행 → 원문 재등록으로 원문/영수증 338건·미전송 0·held 4·소유자 바인딩과 중복 방지를 확인했고 실행 중인 큐는 변경하지 않았다. 원문·영수증·상태·바인딩 집계 해시도 복원 직후 일치했다. 후속 Python 39개·Node 81개 검사 통과. **Supabase의 고객/문의/Action/회신/제품 연결을 포함한 전체 DB 복원 검수는 여전히 미완료**다.

분류 검토 화면 연결 구현(2026-10-07): CRM에 분류/검토 상태 필터, 제안·근거/참조 고객, 사용자 확정/수정과 오늘 검토본 연결 버튼을 추가했다. 좁은 창에서 빠져 있던 Outlook 메뉴도 추가했다. 제안·확정 이력 테이블과 security_invoker view/RPC를 새 Supabase에 증분 적용했다. 실제 DB 합성 ROLLBACK 검사에서 소유자·미허용/익명 접근통제, 응답 유실 재시도, 늦은 수정 충돌, 새 제안의 사용자 확정 덮어쓰기 방지, 원문/문의 연결/업무 제외/보류 보존을 확인했다. UI 합성 계정에서 분류 확정·수정·재조회·필터와 좁은 창 메뉴를 확인했다. 최종 Node 88개·Python 64개 검사 및 빌드가 통과했다.

사용자 로그인 후 실제 연결(2026-10-07): 오늘 검토본의 신규 4건을 인증 API로 연결하여 운영 메일/로컬 영수증 342건·미전송 0이 됐다. 받은 메일 제안 295건과 사용자 확인 스팸 2건을 서버에 저장했다. 긴 본문 4건은 서버 본문 null·로컬 원문 보존이며 기존 문의 연결 1·제외 0을 유지한다. 기존 338건의 원문/상태 집계 해시와 로컬 ID/영수증/소유자 바인딩이 그대로이며, 전체 342건의 식별자·원문 해시·본문 또는 보류 조건과 295건의 제안 메타데이터를 DB와 전수 대조했다. 스팸 2건의 상대 역할은 미확인으로 유지한다.

첫 전송은 제안 153건 후 HTTP 520으로 중단됐다. 같은 요청 ID의 재시도를 최대 3회로 제한하는 공통 처리에 520을 추가하고 Python 66/66·Node 88/88 검사를 통과한 뒤 실제 295건까지 복구했다. 520의 구체적인 서버 원인은 확인하지 않았다. 사용자 확인 스팸 1건의 동일 분류 저장 성공 응답을 한 번 숨기는 통제된 시험에서 입력/요청 ID 유지 → 재시도 → 버전 2 최신 조회를 확인했다. 확정 이력은 3건에서 늘지 않았고 재시도 전후 이력 ID/시각 해시가 일치했다. 실제 장애 복구와 통제된 응답 유실 시험을 구분한다. 웹/API 변경이 없어 직전 88/64 검사와 빌드 결과를 이번 새 빌드 통과로 주장하지 않는다.

일반 서버 재시작 후 명시적 재연결에서 제안 295건·확정 2건·최신 버전 2/이력 3건과 제안/확정 ID·생성 시각 해시를 그대로 유지했다. 원래 승인 기간 실제 재수집은 신규 0·중복 338이며 338건의 원문 키/해시가 사전 캡처와 일치한다. 이후 총 메일/영수증 342·미전송 0과 넓어진 로컬 보관 범위를 유지했다. 실제 DB 소유자 조회·미허용/익명 차단, 원문 수정 차단 및 분류 RLS/invoker/이력 수정·삭제 차단 확인, 재시작한 HTTP API의 익명/무효 토큰 401·다른 Origin 403도 통과했다.

이 연결은 확정 정답 295건이나 모델 학습 완료를 의미하지 않는다. 실제 AI 모델 학습·외부 AI 호출은 0이며 분류별 정답/독립 평가 표본, 두 실제 세션 경합·전체 DB 복원·1주 실사용은 남아 있다. 오늘 수집은 11:14 확인 당시 받은 편지함 5건(11:15 미만 조건)이며 이후 도착 메일·정크 폴더 전체 수집으로 확대하지 않았다.


업무 단계 검토 구현(2026-10-07 후속): 선택 메일의 최신 본문과 같은 수집 scope/대화 식별자의 기록으로 요청/중간 답변/추가 확인/이후 수신 재검토, 업무 목적·대기 대상·다음 할 일/한계를 제안한다. 영문·한국어·중국어 인용 경계를 공통 보완했다. 인증 API는 Auth·허용목록·소유자 RLS의 서버 키/해시 확인 후 로컬 소유자·원문 SHA·서버 영수증을 검증한다. 결과에 원문·주소·가격·발췌를 포함하지 않고 조회만으로 분류 정답·문의·Action·회신 상태를 변경하지 않는다. 실패·늦은 응답·로그아웃을 처리한다.

실제 로컬 원문 342건의 업무 제안 조회와 원문/영수증/상태/소유자 해시 보존·보류 4건 유지 통과. 이전 검토와 다른 대화 10개를 추가 평가 후보로 마련했다. gold 추가 0이며 의미 정확도·현재 처리 상태 확정과 구분한다. Outlook 정상 폴더 48개에서 받은 295키를 전부 찾았지만 현재 Inbox 밖 사례가 0이라 실제 폴더 이동 검수는 남았다. 문의 자동 생성·메일 자동 발송·첨부 열기·AI 호출은 없다.

### 2026-10-07 MVP 1차 잔여 실제 검수 추가

실제 후속 수신 메일 한 건을 기존 문의에 연결했고, 기존 문의에서 원래 메일과 후속 메일 2건을 확인했다. 새 Supabase 읽기 전용 집계에서도 연결 2·문의 4·Action 5를 확인했다. 신규 문의 생성이나 단계 자동 변경은 하지 않았다. 실제 Outlook 이동/복원에서는 EntryID가 바뀌어도 source_key와 본문이 유지되고 원래 폴더·읽음 상태·운영 큐 SHA-256이 보존되는 것을 확인했다. 이동 중 서버 재수집 검수와는 구분한다.
